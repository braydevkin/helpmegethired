## Summary

A Candidate now reaches the platform without a password and leaves it with a Profile. Signing up and signing in happen through a one-time code sent by email, the Candidate uploads a Resume PDF straight to object storage and watches the extraction progress, and the platform parses that Resume into contact details, experiences, education, skills, projects, languages and certifications, then presents the Profile for review and confirmation. Underneath, the ingestion queue moved to BullMQ on Redis with its own worker service, Uploaded Resumes live in S3-compatible object storage with presigned uploads and a reconciliation job that rescues silent and orphaned uploads, every Candidate-owned row is readable only by its own Account, and the API is described by an OpenAPI document generated from the shared schemas.

## Breaking changes

**Passwords are gone.** ADR-0017 replaces them with one-time email codes. Migration `0004` drops `accounts.password_hash` and creates `verification_tokens`. The sign in and sign up contract changes with it: a Candidate requests a code and verifies it instead of posting a password. Existing Accounts are not affected beyond that; they keep their email and receive a code on the next sign in. Migration step 3.

**The queue backend changed.** ADR-0020 replaces pg-boss with BullMQ on Redis, consumed by a separate `worker` service. Redis becomes a required dependency and the `pgboss` schema is no longer read or written. Migration steps 1 and 2.

**Object storage is required.** ADR-0021 stores Uploaded Resumes in an S3-compatible bucket reached through presigned URLs, so the bucket and the `S3_*` configuration must exist before the API starts. Migration steps 1 and 2.

## Migration steps

In order.

1. **Extend the configuration.** Copy the new variables from `.env.example` into the root `.env`. Beyond the v0.1.0 set, the compose stack now reads `REDIS_PORT`, `STORAGE_PORT`, `STORAGE_CONSOLE_PORT`, `QUEUE_DASHBOARD_PORT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`, `PRESIGN_EXPIRES_SECONDS`, `WORKER_CONCURRENCY`, `EXTRACTION_TIMEOUT_MS`, `STALE_PROCESSING_MINUTES`, `AUTH_SECRET`, `AUTH_RESEND_KEY` and `EMAIL_FROM`. The API additionally requires `REDIS_URL`, `S3_ENDPOINT` and `S3_PUBLIC_ENDPOINT`, which the compose file sets itself. `AUTH_SECRET` is mandatory; without `AUTH_RESEND_KEY` the one-time code is written to the log by the fallback sender instead of being emailed.
2. **Start the new services.** The stack gains `redis`, `storage` (RustFS), `storage-init` (creates the bucket), `worker` (the BullMQ consumer) and `queue-dashboard`, bound to localhost. The API image installs `poppler-utils` for `pdftotext`; rebuild it rather than reusing the v0.1.0 image.
3. **Apply the database migrations** with `pnpm db:migrate`, which the compose `migrate` service runs before `api` and `web` start. This release adds three, in order: `0004-replace-passwords-with-one-time-codes`, `0005-create-uploaded-resumes`, `0006-create-profile-tables`.
4. **Drop the unused pg-boss schema.** The application no longer touches it. `DROP SCHEMA pgboss CASCADE;` once the worker is running on BullMQ.
5. **Nothing to backfill.** `ingestions.source` is added with a default of `upload` that is dropped right after, so existing rows are already correct.

## Verification

There is still no deployed test environment; the deployment target remains a pending decision in `docs/adr/README.md`. Verification for this release was done on the CI pipeline and on the local compose stack by @braydevkin:

- Every included pull request passed the CI checks on `develop`: lint, typecheck, unit, integration against a Dockerised PostgreSQL, Redis and RustFS, and the Playwright suite against the whole compose stack. The `Codacy Static Code Analysis` gate was green on every pull request from #63 onwards.
- The Playwright suite covers the passwordless account flow end to end, including a wrong code, a single-use code and a replaced code, and takes a Resume from the upload page through the percentage reaching 100 to the Profile being reviewed and confirmed, plus a PNG refused in the browser.
- The API end-to-end scenario drives the four resume routes against the real queue, worker and bucket: a synthetic resume reaches a confirmed Profile, a hostile file fails with its error code, and every route is refused without a Session.
- The migration suite reverts every migration and applies them all again.
- The parser is measured against a synthetic corpus of thirty resumes through the snapshot harness.

## Rollback

Return production to the `v0.1.0` tag and revert the migrations added here with `pnpm db:migrate:down`, run three times: `0006` drops the Profile tables and the `ingestions.source` and `ingestions.completed_at` columns, `0005` drops `uploaded_resumes`, and `0004` drops `verification_tokens` and restores `accounts.password_hash`.

Reverting `0004` restores the column, not the data: the v0.1.0 hashes were deleted when the column was dropped, so `password_hash` comes back with an empty default and every Account has to set a password again. Restore the database from a backup taken before this release if the Accounts matter.

Uploaded Resume objects stay in the bucket after `0005` is reverted, because the rows that reference them are gone; empty the bucket by hand or leave it for the sweep in the next release. The `redis` and `storage` services can then be stopped; v0.1.0 does not use them.
