## Summary

The first slice of the candidate journey reaches production. A Candidate can create an Account, sign in, and land on the journey page that will host the next steps. Behind it, the platform now has its foundation: the monorepo with the shared schemas, the Next.js and NestJS applications, PostgreSQL with pgvector behind Kysely migrations, the Docker Compose stack, the CI pipeline, and the profile ingestion design with its persisted segment state machine on a PostgreSQL-backed queue, ready for the first Resume processor.

## Migration steps

1. Provide the runtime configuration. The compose stack reads a root `.env` copied from `.env.example` (`WEB_PORT`, `API_PORT`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`). The API reads `NODE_ENV`, `PORT`, `WEB_ORIGIN` and `DATABASE_URL`; the web app reads `API_URL`. The compose file sets the API and web variables itself.
2. Apply the database migrations with `pnpm db:migrate` (the compose `migrate` service runs it before `api` starts). This release ships three migrations, in order: `0001-enable-vector-and-create-accounts`, `0002-add-account-credentials-and-sessions`, `0003-create-ingestions-and-segments`.
3. The job queue needs no extra service: pg-boss creates and migrates its own `pgboss` schema in the same database when the API starts.
4. The `Board` GitHub Actions workflow needs the `PROJECT_TOKEN` repository secret, a classic-scope token with `project` and `repo`. This is a repository setting, not a runtime one.

## Verification

There is no deployed test environment yet; the deployment target is a pending decision in `docs/adr/README.md`. Verification for this release was done on the CI pipeline and locally by @braydevkin:

- Every included pull request passed the five CI checks on `develop`: lint, typecheck, unit, integration against a Dockerised PostgreSQL, and the Playwright suite against the whole compose stack.
- The Playwright suite covers the home page and the account flow: sign up, journey page, sign out, sign in, redirect when signed out, inline validation, wrong password, duplicate email.
- The migration suite reverts every migration and applies them all again.
- The ingestion suite exercises resume after a failure, the single-active rule, and one run through the real pg-boss worker with a retry.

## Rollback

There is no previous production version to return to. If the release has to be withdrawn, stop the stack with `docker compose down` (add `--volumes` to drop the data), or revert the three migrations with `pnpm db:migrate:down` run three times, which also removes the `accounts`, `sessions`, `ingestions` and `ingestion_segments` tables and the `vector` extension. The `pgboss` schema is not touched by the application migrations and can be dropped by hand.

## Known issues

- Password reset, email verification and rate limiting on sign in do not exist yet (follow-ups in ADR-0013).
- The ingestion module has no real segment processor and no progress endpoint; the Resume PDF processor and the progress display are the next tasks of the Account and Profile milestone (follow-ups in ADR-0014).
- Pending decisions: license, LLM provider, deployment target, LinkedIn data access (`docs/adr/README.md`).
